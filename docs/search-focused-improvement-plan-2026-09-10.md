# 搜索命中与主模型成本优化计划

状态：历史计划，部分实施。根据 2026-09-10 对话确认的目标整理；取代早先调研中的 Deep Research 工作流建议。

## 实施结果（截至 0.4.0）

- S1–S3 已落入当前 Skill、README 和 MCP 工具说明：保留用户约束、取消固定选读数量、仅粗排明确无关候选并按具体缺口补搜。
- S4 采用宿主中立的 `references/subagents.md` 实现，不在仓库硬编码私有模型或安装全局角色模板。
- S5 未实施；没有把 Pi 或 pi-graph 变成项目依赖。
- S6 只完成接口回归、静态检查和一次 Codex 委派 smoke；没有完成计划中的 A/B/C 定量对照，因此不声称整体成本或命中率提升。

以下保留原计划和取舍依据，不能视为全部已交付。

## 目标与范围

让用户更快找到想要的页面、项目、讨论或答案，并减少主模型阅读无关候选的开销。保持一个 Skill、一个 Core、CLI/MCP 两个薄入口；不把项目扩展为研究平台。

本轮拟合并的内容是搜索使用策略、可选的宿主子 Agent 模板、以及小规模对照验收。没有证据支持现在修改 RRF 算法或给 Core 增加模型依赖。

成功应同时看目标命中、漏选、时间和模型用量。总 token 不一定减少；单独报告主模型和子模型用量。费用只在实际用量及计价可确认时计算，不能用 API 价格直接推算 Codex 订阅额度。

## 合并清单

| 编号 | 类型 | 工作项 | 优先级 |
|---|---|---|---|
| S1 | 优化 | 搜索目标与约束明确化；查询变体服务于同一个目标 | P0 |
| S2 | 优化 | 按需选读、确认目标即停止；替换固定选读 3–5 篇的要求 | P0 |
| S3 | 优化 | 用“直接命中／待确认／明显不符”检查候选，必要时定向改词补搜 | P0 |
| S4 | 新增，可选 | 搜索筛选子 Agent 的最小交接约定与 Codex 配置示例 | P1 |
| S5 | 新增，可选 | Pi 单节点 search-filter 流程示例，复用已有 pi-graph 与 CLI | P1 |
| S6 | 验证 | 当前流程、优化后直读、优化后委派三组对照与兼容性验收 | P0 起步，贯穿全部阶段 |

P0 先完成并验证，P1 再以显式启用方式试用。少量、明确的搜索继续直接执行，不强制每次启动子 Agent。

## S1：让查询围绕要找的内容

- 从用户请求保留对象、版本、平台、时间和排除项，以及想找的内容类型。没有提供的约束不擅自补成硬条件。
- 保持原始 `query`；需要变体时，使用同一目标的别名、页面常用术语、中英文表达或精确报错。复用现有 `expand`，不新增服务端查询生成器。
- 精确名称、URL、错误码等明确请求不强制展开。首轮有歧义或实际结果揭示别名时，才有目的地补充查询。
- 已知链接直接 fetch；已知平台按现有 `sources`/`route` 选源，不新增复杂路由规则。
- 对用户明确要求的比较或多个结果，保留相应范围；“找到即停”不意味着只满足其中一个要求。

涉及：`skills/multi-search/SKILL.md`、`skills/multi-search/references/cli.md`。查询归一化与两级 RRF 实现不变。

验收：精确报错不丢版本或平台；变体不扩成无关研究方向；已有 URL 不重复泛搜。

## S2：按需求决定读多少

当前 Skill、README 及 MCP 描述多处要求选读 3–5 篇，并逐篇取得全文。这是本次要明确改变的调用方行为。

- 找指定页面／仓库：核对身份及必要页面信息即可结束，不为凑数再读其他来源。
- 找具体答案／解决办法：读取能验证该答案的正文位置；预览不足时使用已有 `read_source` 或 fetch；确实需要上下文时再读全文。
- 只有片段经过检查，就只声称检查了该片段，不能称为已读全文。预览没有出现答案不代表整页没有答案。
- 比较、罗列多个资源等请求按用户所需数量和覆盖面选读；不统一改成固定 1 篇或固定 3 篇。
- 保留按版本核对、引用原始来源及页面内容不可信的规则。定位一个链接不自动触发完整研究；作出事实性结论仍需相应证据。

涉及：`skills/multi-search/SKILL.md`、`skills/multi-search/references/cli.md`、`multi_search_mcp/server.py` 的工具说明、`README.md` 的当前流程及例子。历史验收报告保留其当时行为，不改写旧结果。

兼容边界：Core 仍按 RRF 获取最终最多 15 个正文，原有 JSON 字段、排序、预览、缓存和 `full_content` 参数语义不变。本步骤减少 Agent 读取量，不声称减少了 Core 的抓取请求。

验收：已有足够证据时不为凑数 fetch；片段不足时不提前宣称命中；全文入口仍可正常使用。

## S3：候选匹配与有限补搜

判断发生在调用方 Agent，不新增 Core 分数或不可解释的“命中概率”。检查对象、约束、内容类型和是否直接包含目标内容。

| 标签 | 含义 | 后续动作 |
|---|---|---|
| 直接命中 | 当前已检查内容直接满足目标，且无已知约束冲突 | 优先提供；需要事实核验时读必要正文 |
| 待确认 | 主题或身份相关，但预览不足、版本不明或正文不可得 | 保留候选，必要时进一步读取 |
| 明显不符 | 已观察到对象、版本、平台或内容类型与请求冲突 | 不优先返回，保留可追溯引用 |

- 不因某条结果被多个 provider 命中，就当作语义上更符合需求。
- 首轮未找到目标时，利用候选中实际出现的别名、版本、链接或报错线索修正查询。复用既有停止规则；不能连续换同义词无效循环。
- 区分“本次候选中未找到”“候选待确认”和“搜索／抓取失败”，不能把服务失败报成没有结果。
- 不把 RRF 前 15 条外的内容断言为不存在。候选筛选只能改善已有候选的选择，不能恢复未召回内容。

涉及：与 S1/S2 同一份 Skill；不再新增一套独立规则文件或关键词评分器。

验收：标题相似但版本错误的结果不误选；答案位于预览之后的页面不直接淘汰；失败信息保留。

## S4：可选 Codex 搜索筛选子 Agent

流程：主 Agent 传搜索目标及约束 → 小模型子 Agent 自己调用 multi-search → 子 Agent 检查候选并交回少量结果 → 主 Agent 按需读原文。

关键约定：

- 委派发生在搜索之前，主 Agent 不先接收完整搜索响应。仅发送必要任务上下文，避免复制整段对话。
- 子 Agent 只负责查找和筛选，不生成研究报告，不递归启动更多子 Agent。
- 小模型明确配置，不默默继承昂贵的主模型。仓库模板不写用户私有 provider 别名、凭据或绝对安装路径。
- 交接包含原始 `source_id`、URL、标题、匹配标签及一句有材料依据的说明；只在需要时附短原文片段及位置。不得改写出源文中没有的事实。
- 同时交回必要的待确认候选、搜索/抓取错误和“未选候选数量”。不回传全部正文或完整过程日志，不强制凑固定数量。
- `source_id` 必须来自真实工具响应。子/主 Agent 使用相同状态存储时验证其可用性；状态不共享或引用过期时，主 Agent 用已观察到的 URL 显式重新获取。
- 不把“待确认”全部删除来制造 token 节省。首版不做永久候选排除，也不写新的长期证据数据库。
- 显式选择委派后，如果角色、模型或工具不可用，报告具体失败，不悄悄切换成另一条路径并声称委派成功。

拟新增：

- `skills/multi-search/references/delegated-search.md`：通用交接约定和启用条件，主体保持简短。
- `skills/multi-search/assets/codex/search-filter.toml`：专用角色模板。
- `skills/multi-search/references/codex.md`：模板安装、模型选择、调用示例及核验方式。

模板在用户选择安装时复制到 Codex 的用户或项目 agents 目录，不随 Python 包安装自动改写全局配置。保留现有 explorer 等通用角色，不原地改变其职责。模板具体模型在安装/启用时按可用列表确定，未配置完整不能宣称可运行。

权限验收需考虑 CLI 正常写入 SQLite 缓存：不能因为角色叫“只读”就假设缓存可写，也不擅自提升宿主权限。子 Agent 不修改项目文件，沿用已授权的工具与运行条件。

本会话已确认 Codex 支持子 Agent 独立模型配置；当前本机 explorer 配置为 gpt-5.4-mini/low，但尚未试运行搜索筛选任务。[官方配置说明](https://learn.chatgpt.com/docs/agent-configuration/subagents)

## S5：可选 Pi 接入

复用用户当前安装的 `@shying/pi-graph` 0.2.0，提供单个 agent 节点的 search-filter 示例。主 Pi 会话就是结果接收方，不再在图里另建一个昂贵的 writer。

- 节点显式指定小模型、`context.mode = "isolated"`，接收必要查询和约束。
- 节点通过命令工具调用 multi-search CLI；Windows shell、可执行路径、provider 加载和凭据可用性均在实际宿主验证。
- 自定义 provider 可能依赖扩展加载，不能一律设置 `loadExtensions=false`。限制暴露的工具，禁止图递归，不为了搜索安装 MCP 适配器。
- pi-graph 的 `readOnly` allowlist 不允许任意 shell；需要运行 CLI 时，应按该版本的真实工具配置执行，不能提供“readOnly=true 同时 bash 执行 CLI”的无效例子。
- 交接遵循 S4，相同的 URL/ID、待确认与失败语义。
- 当前存在的 `Explore.md` 不自动等于图配置；不把该文件中的私有模型别名复制进公开模板。

拟新增 `skills/multi-search/assets/pi/search-filter.json` 与 `skills/multi-search/references/pi.md`。安装后使用 `/pig validate search-filter` 验证，再由主模型调用 `pi_graph_run`；`/pig run` 可作独立冒烟检查。没有 pi-graph 的用户仍可直接使用 CLI，本项目不将图扩展列为必装依赖。

已核对本地 pi-graph 的 node model/context 字段和 CLI 接法，但还未进行真实节点执行。相关一手资料：[Pi 子 Agent 示例](https://github.com/badlogic/pi-mono/tree/main/packages/coding-agent/examples/extensions/subagent)、[pi-graph](https://github.com/huang-sh/pi-graph)。实施时以安装版本的 schema 校验为准。

## S6：如何证明优化有效

### 对照设计

先建立小规模测试集，建议 12 个明确搜索任务，覆盖：指定仓库/页面、版本限定、精确报错、中文描述对应英文内容、目标不在预览开头、无结果/部分失败。目标 URL 或可接受材料及判定理由独立标注；错误版本和预览不完整用例必须包含。

比较三组：

1. A：当前 Skill，主模型直接搜索选读。
2. B：S1–S3 优化后的 Skill，主模型直接搜索选读。
3. C：与 B 相同的搜索规则，由小模型先筛选，主模型只读交接结果。

A/B 区分“规则调整”的收益；B/C 才能衡量“模型分工”的收益。先用固定候选和正文对比筛选，再用新问题做真实搜索端到端验收，避免把搜索引擎波动当模型差异。开发题与验收题分开，不在同一批题上反复调规则后宣称普遍提升。

### 指标与门槛

- 目标是否找到、首个有效结果位置、用户看到的前 5 条是否包含有效目标；需要完整集合的任务另外检查覆盖。
- 子 Agent 是否漏掉候选中本来存在的有效目标；明确“召回失败”和“筛选失败”。关键样例不能用平均值掩盖退化。
- 主模型和子模型分别记录 input/output/cache/reasoning usage；工具返回字节数仅作诊断，不能冒充 tokenizer 实测。
- 记录整体耗时、搜索调用、正文读取、小模型轮数；费用或额度不可确认时填 unknown。
- 正文失败、非法或伪造 source_id、空交接、模型不可用均显式失败；待确认候选可以触发进一步读取。
- 默认启用委派的前提是新问题验收中目标命中不退化、主模型用量降低且整体成本/时间符合预先选定的要求。若实际总成本或订阅额度无法核验，只声称减少了主模型输入，不声称总体更省。

这是小样本试验，不是通用准确率保证。开始实际模型调用前记录所选模型、规则版本和验收标准；不会凭空指定已达到的节省比例。

### 复用现有验证

- `scripts/source_trace_fixture.py` 可复用接口、引用和失败边界，但其所有查询返回同一候选集合；不能直接衡量改词补搜的召回收益。
- `scripts/evaluate_query_fusion.py` 验证排序相关实验，不拿排序快照代替 Agent 筛选/回答验收；不变更已有 RRF 评测冻结策略。
- 文案修改检查接口说明与 Skill 一致；涉及现有公开行为的相关回归命令：

```powershell
.venv/Scripts/python.exe -m unittest test_candidate_search test_search_fetch_pipeline test_search_preview test_full_content_interfaces test_full_content_flow test_cli test_cli_failures test_content_store test_fetch_url_cache -v
```

- 对新增交接/宿主模板测试真实调用边界与失效条件，不用“提示词包含某个单词”的测试证明模型遵循规则。Codex/Pi 各至少完成一次真实搜索、主模型按引用读正文以及一次明确失败场景。
- 若之后改安装/打包路径，再运行 `scripts/smoke_install.py` 及独立安装验证；本阶段不因只有文档和模板变更而无条件重装全局工具。

## 实施顺序与交付

1. **建立基线：**冻结小批搜索目标和评估方式，记录 A；不先修改旧验收结果。
2. **调整搜索规则：**一次提交完成 S1–S3 及 README/MCP 描述同步，跑 B 对照。若命中退化，修正规则再继续。
3. **实现可选委派：**先定义 S4 交接与 Codex 模板，再落 S5 Pi 模板。两种宿主复用同一规则，不复制出两套搜索逻辑。
4. **验收与交付：**执行 C 和两个宿主的接入测试，报告实测成本/遗漏/耗时，补启用说明。默认保持显式选择委派；未经效果验证不将所有搜索自动交给小模型。

本计划只涉及仓库内文件。安装个人角色、启用 Pi 图、选择具体模型和更新个人 Skill 是后续实施时单独可核验的部署步骤；不把本机已有配置当作其他用户的安装前提。

## 本轮不合并

- Deep Research 研究任务状态、递归调查、证据台账、报告生成和长期知识库。
- 本地 reranker、向量数据库、PyTorch/GPU 依赖。
- Core 内置 LLM、远程模型 API key 或自动切换模型服务；宿主委派已足够覆盖当前需求。
- 全量引入 LangGraph、GPT Researcher 或 DeerFlow。
- 新增搜索源、重写 RRF、静默过滤公开搜索结果、自动减少 Core 的 15 条正文获取。
- 泛化的自动调参、评分仪表盘或默认开启多 Agent。

若试验表明主要瓶颈是网络抓取或预览信息不足，再凭实际失败样例单独立项；不把它们预先塞进本次改动。
