# 全面代码审查（2026-10-22）

范围：Python 包 `multi_search_mcp`（架构；正确性与安全）、Tauri/Rust 后端 `desktop/src-tauri`、桌面 UI `desktop/ui`，以及仓库卫生和文档。只读审查，未修改代码。

## 测试与构建现状

- Python：`python -m unittest discover -s tests -t .` 共 810 个测试全部通过，5 个 skipped。`.venv` 中没有安装 pytest。
- Rust：`cargo test --no-default-features` 约 175 个测试通过，2 个 ignored。
  - 默认特性下 `cargo check` 和 `cargo clippy` 失败，原因是缺少生成产物 `resources/cli-bundle`。
  - 因此 `window.rs` 中的 30 个 Tauri 命令既没有被编译检查，也没有测试。
  - `install-test-boundary` 特性下的测试套件未运行。
- 前端：未安装 `happy-dom`，9 个测试文件中只有 `payloads.test.js` 能运行（7/7 通过）。页面级结论仅来自读代码。
- CI：使用 `pip install .`，不经过 `uv.lock`，依赖版本不固定。

## 一、优先处理（正确性 / 安全）

1. **Tauri 攻击面过大**
   - capability 的 `permissions: []` 并不约束 app 自定义命令：build.rs 没有用 `AppManifest` 声明命令，30 个命令全部对页面开放。
   - 同时开启了 `withGlobalTauri: true`。
   - 前端把后端错误字符串直接拼进 `innerHTML`（`desktop/ui/sources.js:45`、`desktop/ui/settings.js:44`），provider label 也做了插值。
   - 测试辅助接口编译进了正式库（`desktop/src-tauri/src/lib.rs:55-338`），其中包括可运行任意程序、绕过校验写入加密库的接口。
2. **明文 Key 暴露**
   - 进入凭据页时会自动展开第一个源，并解密显示明文 Key（`desktop/ui/sources.js:313`、`credentials.js:169-174`），没有掩码。
   - `credential_read` 把全部明文 Key 返回给 WebView。
   - 删除行时要求前端回传明文快照作为乐观锁。
   - `detect_cli`、`start_test_search`、`credential_test` 接受前端传入的任意 exe 路径。
3. **搜索 query 参数注入**：`desktop/src-tauri/src/execution.rs:141-149` 把 query 作为位置参数传入，前面没有 `--`，`--source=...` 这类值可以绕过白名单。
4. **桌面端变更操作无互斥，执行状态锁中毒后无法恢复**
   - 安装、更新、卸载以及 Skill 的安装、更新、删除都可以并发执行，可能破坏 `active.json`。
   - `managed-skills.tmp` 使用固定文件名，并发时会丢记录。
   - `execution.rs:134,172` 使用 `lock().unwrap()`，锁中毒后只能重启应用。
   - 取消搜索时会在 IPC 线程上持锁等待子进程退出。
5. **key 熔断状态会被并发覆盖**：`multi_search_mcp/src/state/key_state.py:216-266` 中，一次超时或网络错误会把 key 恢复为 ACTIVE，清掉其他请求刚写入的配额耗尽、冷却状态和连续 401 计数。
6. **截止时间后无限等待**：`multi_search_mcp/src/support/concurrency.py:108-118` 在到期后仍对每个 future 调用不带 timeout 的 `result()`，只要有一个任务卡住，整个 search 就会挂起。
7. **fake-IP 代理下抓取全部失败**
   - Clash 等代理会把域名解析到 198.18.0.0/15，本地 DNS 预检判定为私有地址并拒绝（`scrape/scrape.py:239,420-425`、`scrapers/_eddrit.py:147`、`scrapers/reddit.py:118`）。
   - 对固定端点做 DNS 预检本身也没有安全价值。
8. **前端切页竞态**
   - `desktop/ui/app.js` 不会取消过期的 mount。
   - `install.js` 和 `skill.js` 的 `dispose` 基本是空的，异步回调会写进新页面的 DOM。
   - mount 抛错时没有兜底，会直接白屏。
9. **"请重试"实际无效**：`desktop/ui/credentials.js:17-45` 会永久缓存失败的 provider 加载 promise，只有重启应用才能恢复。

## 二、架构

- **分层越界**
  - `search/snapshots.py:104-106` 在函数内反向 import core。
  - `search/resolve.py:8` 依赖 scrape，导致默认 scrape backend 顺序存在两份（`resolve.py:39` 和 `scrape.py:65`）。
  - support 层混入了凭据库（SQLite/DPAPI）和领域策略。
- **缺少 Provider 抽象**
  - 新增一个 provider 需要改 4–6 处：`capabilities.py`、`registry.py`、`search_runner.py`、`keys.py`、`scrape.py`、`scrape_pipeline.py`。
  - `registry.py:53-136` 中有 12 段几乎相同的 lambda，参数顺序互不一致。
  - `call_optional_timeout` 通过参数名隐式适配，签名漂移时会静默失效。
- **HTTP 样板重复**：约 9 个 searcher 重复"请求 → 解析 JSON → 返回错误行"的流程，只有 github 和 tavily 产出结构化的错误类别。
- **错误模型有两套**
  - `_row_kind` / `_row_origin` 有三份实现，且互不一致：`support/auth.py:33-68`、`state/key_state.py:304-331`、`search/search_runner.py:324-333`。
  - `kind`/`error_type`、`origin`/`error_origin` 新旧字段并存。
  - 同一个错误可能被分到不同类别，进而影响 key 轮换。
- **上帝函数**
  - `core/search_pipeline.py:51-269` 的 `run_search_candidates` 有 219 行。
  - `core/body_fetch.py:76-240` 的 `run_fetch_source` 有 165 行。
- **渲染分散在三处**：`cli.py`、`core/present.py`、`support/format.py`。CLI 自称"薄入口"，却在里面计算业务 outcome。
- **两个公共搜索入口**：`run_multi_search` 和 `run_search_web` 会重复解析同一个请求。`ResolvedSearchPlan` 中混有兼容遗留字段。
- **并发与超时**
  - 三个全局线程池在 import 时创建。超时线程长期占用槽位、无法取消，长驻进程下可能耗尽线程池。
  - 池容量与 `scrape_concurrency` 无关。
  - 只有部分 provider 会把 deadline 一路传到 `urlopen_retry`。
- **缓存失效范围过大**：cache_scope 对全部 `runtime_keys` 做哈希，任意无关 provider 轮换 key，所有正文缓存都会失效。
- **Twitter 凭据键名不统一**：同一个凭据有 `twitter`、`twitter_cookies`、`twitter_cookies_path` 三个键名。
- **Rust 模块职责重叠**
  - Skill 逻辑分散在 `skill.rs`、`skill_manage.rs`、`skill_common.rs`。
  - marker 校验有三套实现。
  - 存在多余的转发层；`install.rs` 重复实现了 skill 目录解析。
- **死代码**
  - `keys.pick_key`、`keys.key_pool` 已无调用方。
  - 存在未使用的 import。
  - `support/config.py` 中的 `CONFIG_ENV_VAR` 是死常量。
  - `_prepare_scrape_target` 返回两个相同的值。

## 三、健壮性与安全（中）

- **SSRF 校验与实际连接脱节**
  - 校验和连接各自解析一次 DNS，连接时的解析结果不再检查，存在 DNS rebinding 窗口。
  - 配置了环境代理时，本地校验完全失效。
  - NAT64、6to4 地址是否被拦截取决于 Python 版本。
- **大页面直接失败**
  - 抓取上限按"字符"计算，缓存上限按 256KB "字节"计算，中文页面约 8.5 万字即超限，整个 fetch 失败。
  - `tests/test_full_content_flow.py:112` 把这个行为写成了预期。
- **付费 POST 自动重试**：遇到 SSL/EOF 错误会自动重试，可能重复计费（`support/http.py:246-256`）。
- **响应体无大小上限**：读取时不限大小，Brave 的 gzip 解压也不限大小。
- **DNS 线程池过小**：只有 8 个 worker，池满即拒绝，而抓取池有 30 个线程，DNS 一慢就会批量误报失败。
- **SQLite 并发设计偏弱**
  - 没有开启 WAL，每次操作都新建连接。
  - 每个进程启动时都要抢一次写锁做迁移。
  - 选 key 不是原子操作。
- **敏感数据落盘**
  - site_memory 原样持久化 URL（可能带 token）和原始错误信息，且永不清理。
  - Twitter cookies 以明文 JSON 存储，读取时不兼容 BOM。
- **Rust 脱敏不完整**
  - `redaction.rs` 的规则与 `process.rs` 的 `ENV_SECRET_MARKERS` 不一致，也没有纳入 settings 中保存的 cookie 路径。
  - 极短的 Key 会把输出里所有相同的字符都替换掉。
  - 每次 probe 都要用 DPAPI 解密全部 9 个凭据。
- **桌面端性能问题**
  - 同步命令在 IPC 线程上执行 SQLite（busy_timeout 5 秒）和注册表操作。
  - 每次检查安装状态都要对整个 runtime 全量计算 SHA-256，并多次启动 CLI。
- **Rust 端其他问题**
  - jina 凭据保存的读改写不在同一个事务里。
  - Skill 安装没有检查 `.claude` 路径链上的 junction。
  - 子进程输出在 4 MiB 处截断，但截断不可感知。
- **契约测试无效**
  - `tests/ui_contract.rs` 中的 `emit_types_d_ts` 在普通 `cargo test` 中就会改写 `types.d.ts`，漂移检查因此失去意义。
  - 命令名和参数名没有自动对比；手工核对过，目前一致。
- **CLI 低风险项**
  - 异常文本输出前没有做 scrub。
  - `keys reset` 不带参数就会重置全部 key，包括人工禁用的 key。
  - Windows 下 stdout 使用 `errors=strict`，遇到孤立代理字符会报错。

## 四、UI / 视觉

- **小字与低对比度**
  - CSS 中有 8px×2、9px×6、10px×30、11px×20 处字号。
  - `--muted: #78879b` 的对比度约 3.6:1，低于 WCAG AA 的 4.5:1。
- **没有设计 token 体系**
  - `styles.css` 中有两套 `:root` 互相覆盖。
  - 有 146 个硬编码颜色，多种相近的绿色混用。
  - 没有 spacing、radius、字号变量，也没有暗色模式。
  - 用 `[data-status]`、`[role=alert]` 这类全局属性选择器挂样式。
- **断点与窗口尺寸错位**
  - 默认 1080 宽的窗口下，sources 页一直处于折叠布局，1350px 和 1600px 的分支用不上。
  - 窗口最小 760px 时，侧栏只剩 132px。
- **反馈与状态**
  - 安装等长操作只显示一行文字，没有进度。
  - 测试搜索直接显示原始 JSON。
  - 危险操作的颜色语义不一致：可撤销的"优先"用红色，"确认恢复"反而用 primary。
- **文案不统一**
  - eyebrow 编号与导航不符：skill 页写"02"，导航是"03"。
  - 标题有的带句号、有的不带。
  - 中英文术语混用。
- **无障碍**
  - 内联确认没有焦点管理。
  - `role=alert` 过多。
  - 切页时没有播报，也不移动焦点。
  - `aria-label` 用在了没有 role 的 div 上。
- **前端代码**
  - 约 8 份重复的 inline-confirm 实现；settings 和 scrape 的草稿状态机几乎是平行实现。
  - 错误归一化逻辑重复了二十多处。
  - 存在四套防竞态计数器。
  - 页面模块 `checkJs:false`，没有类型检查。
  - api.js 没有统一的错误类型。
  - scrape 页保存时使用挂载时的旧快照，会回滚别处的修改。
  - diagnostics 中的搜索源列表是硬编码的，超时 `max=90` 与校验范围 1–60 不一致。
  - 品牌图标是硬编码的，新增 provider 时会显示 undefined。

## 建议修复顺序

1. **安全**
   - 收紧 Tauri capability，关闭 `withGlobalTauri`。
   - 前端不再用 innerHTML 插入动态值。
   - query 前加 `--`。
   - Key 默认掩码显示。
   - fixtures 用 cfg/feature 门控。
2. **正确性**
   - key 状态写入时保留更强的状态。
   - 截止时间后的等待设置上限。
   - DNS 预检兼容 fake-IP。
   - 桌面端变更操作加互斥锁。
   - 修复前端切页竞态和失败缓存。
3. **测试与构建**
   - 声明 pytest 和 happy-dom。
   - CI 按锁文件安装依赖。
   - 让干净 checkout 也能跑 `cargo check`。
   - 修复 types.d.ts 漂移检查。
4. **架构重构**
   - 先统一错误模型和 HTTP 基础件。
   - 再引入 Provider 协议和单一注册表。
   - 最后修正分层、拆分长函数。
5. **UI**
   - 建立设计 token。
   - 加大字号、提高对比度。
   - 以 1080 和 760 两个宽度重做布局。
   - 补齐进度提示、焦点管理和文案统一。
6. **卫生**
   - 清理 `build/` 和 `.scratch/`。
   - 同步 README 和 glossary。
   - 归档历史文档。
